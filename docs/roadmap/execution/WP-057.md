## Trigger (owner machine, live)

After installing the retained `0.1.0-rc.1` Linux candidate on the owner's
Xubuntu 26.04 machine (wrapper SHA-256 `fc608958…d54cda1` verified against
[artifacts.json](../../releases/0.1.0-rc.1/artifacts.json), sidecar checksum
verified, payload verified by the installer, per-user install to
`~/.local/opt/poliscope/0.1.0`, bundled-engine self-test `passed`), a menu
click opened nothing. Reproduction with captured stderr: immediate
`FATAL:sandbox/linux/suid/client/setuid_sandbox_host.cc(166)` exit (rc 133, core
dump) — AppArmor restricts unprivileged user namespaces
(`apparmor_restrict_unprivileged_userns = 1`) and the bundled `chrome-sandbox`
helper ships non-setuid (0755). Two further observations: the candidate ships
no launcher icon anywhere (asar, payload or repository), and
`scripts/freeze_release.py` is hard-labeled `0.1.0-rc.1`, so a packaging
correction cannot produce a valid new candidate receipt without tool edits.

## Scope and implementation

Bounded corrective maintenance that fixes the packaging-layer findings without
touching application behavior:

- `packaging/install-linux.sh`: after the engine self-test, the installer
  prints a non-fatal NOTE describing the sandbox failure mode and its
  remedies; the desktop entry gains `Icon=poliscope`; the candidate icon is
  installed into the user's hicolor icon directory. The installer stays
  per-user, refuses elevation, keeps its payload-hash/exclusive-mkdir
  semantics, and launches nothing.
- `packaging/sandbox-notice.sh`: parameterized helper (sysctl path + restricted
  value) covering both Ubuntu's `apparmor_restrict_unprivileged_userns` and
  Debian's `unprivileged_userns_clone`; tests assert silent/unrestricted,
  absent and restricted branches.
- `packaging/icons` + `scripts/make_icon.py`: a project-owned launcher icon
  (dark ground, amber ring, warm-white centre; no remote artwork; regenerated
  deterministically with the committed translator on a system Pillow).
- `scripts/distribution.py`: bundles the notice and icon into Linux
  candidates; Windows path and signing are unchanged.
- `scripts/freeze_release.py`: `--label` records `0.1.0-rc.N` receipts; the
  active receipt lives in the current label's release directory
  (`DEFAULT` → `docs/releases/0.1.0-rc.2/inventory.ci-history.json`); `verify`
  accepts any well-formed rc label and still rejects everything else. Prior
  receipts, including rc.1's two, remain immutable.
- `docs/native_distribution.md`: new "Linux user-namespace restrictions"
  section with the reproduced failure text and both sanctioned remedies
  (scoped AppArmor `userns` profile matching Ubuntu's chromium/chrome/brave
  pattern, or root-owned mode-4755 `chrome-sandbox`); launcher-icon note for
  Linux installation. rc.1 README records the supersession; the new
  [rc.2 candidate README](../../releases/0.1.0-rc.2/README.md) defines the
  label and what changed relative to rc.1.

## Owner-machine live validation of the remedy (pre-implementation)

On the owner machine, applying the scoped AppArmor profile
(`/etc/apparmor.d/poliscope`, same shape Ubuntu ships for chromium) resolved
the launch: the packaged Electron window opened on `:0` (1040×720), the
renderer confirmed the constrained sandbox (`NoNewPrivs`, `Seccomp: 2`,
`Seccomp_filters: 1`), and the launched process stayed alive with a zero-byte
log. That evidence fixes the diagnosis and both documented remedies; it does
not certify macOS/other distributions, signing, or cross-version loading.
