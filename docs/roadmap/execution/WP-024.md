## Implementation and inspection

The exact [G2 selection](WP-024-selection.json) binds all twelve mandatory subcases
to exact JUnit names across engine, main and packaged desktop tests. CI verifies
fresh candidate/report hashes and requires each selected test exactly once with
no failures/skips; omitted, duplicate, unrelated and future-only selections have
negative checks. Pytest's explicit `test_offline_gate[ID description]` names are
supported alongside existing ID-prefixed desktop names. Future M3/M4/M5/M6/M7
subcases retain their original first gates; no requirements manifest was changed.
This checks application execution, not automatic milestone acceptance.

Packaged keyboard tests create a blank society, retain unanswered choices, inspect
original synthetic option wording, preview/cancel without advancing history,
apply population 125 exactly once, fork the original revision, compare the saved
conditions and cold-reopen the same main context. A separately authored numerical
fixture in the same UI workflow exposes local reserve 0 kg, regional reserve
200 kg, unmet local demand 80 kg, exact accounts, calculation closure and MIT
source text without the fixture's executable model. These are separate stores:
no numerical social effects are invented for qualitative starting interviews.
Existing packaged history/comparison and interview tests cover archived alternatives,
undo/redo/edit-after-undo, incompatible/unknown comparisons, stale apply and private
rationale. Selection and report attachments retain synthetic saved context identities.

HTTP/HTTPS requests in the test app's Electron session are explicitly rejected;
a Session.fetch probe fails. Provider key variables are removed from its launch
environment. File/UI/IPC/engine/database calls are production implementations;
the only dialog override selects isolated temporary directories. Keyboard paths
use focused keys/text and a native select menu, including accounts/trace/fork/
comparison and cold reopen. Inspector opening focuses its close button; closing
returns to the still-connected originating control. The packaged tests assert
that focus recovery and exact text/table equivalents.

Recovery uses a second actual SQLite connection holding BEGIN IMMEDIATE. Failed
Apply leaves the old confirmed revision, labeled unsaved draft and retry candidate;
releasing the lock and retrying produces exactly one durable decision. A real
packaged page-query child is killed with SIGKILL; the request rejects, the saved
context remains labeled confirmed, and reconnect/reopen starts fresh production
children against the same store. Existing publication-stage engine tests separately
verify rollback after partial staged writes. A cold unsupported-protocol producer
is injected only into the main-controller test: the real trusted reader still reads
retained SQLite, edits lack a workspace grant and reconnect cannot silently migrate
or erase that store. Ordinary scope/branch/historical navigation is also selected.

Separate author inspection covered manifest completeness, JUnit identity binding,
cache/runtime-independent historical reads, independent integer/Decimal oracles,
actual process/SQLite paths, cleanup, context labels, retry identity and focus.
A proposed SQLite fault trigger was discarded because the production store correctly
rejects altered schemas; the final fault uses an ordinary competing write lock.
Keyboard tests wait for enabled/focused controls and commit native selection once,
so asynchronous loads cannot type into disabled fields or select an intermediate
branch. Product deadlines, dependency locks and runtime sandbox preferences are
unchanged. Linux Electron checks use the existing test --no-sandbox launch option;
they do not certify OS sandbox enforcement.

## Validation and reproducibility

Frozen npm/uv installs use pinned Node 24.19.0, npm 11.9.0, Python 3.12 and uv
0.12.23, with writable npm/uv/XDG caches under /tmp in this cloud runtime.
Linux packaging bundles the Python/SQLite service. Xorg dummy display :99 supplies
the cloud display; CI uses xvfb-run. Run all three evidence suites on one unchanged
candidate, then bind the complete selection:

```sh
uv run --frozen python scripts/evidence.py engine --output artifacts/engine
uv run --frozen python scripts/evidence.py unit --output artifacts/unit
npm run package
xvfb-run -a uv run --frozen python scripts/evidence.py desktop --output artifacts/desktop
uv run --frozen python scripts/check_gate_evidence.py docs/roadmap/execution/WP-024-selection.json artifacts/engine artifacts/unit artifacts/desktop
```

TypeScript, generated contracts, bootstrap content inventory, roadmap/baseline,
stdlib roadmap tests and whitespace checks are additional checks. An empty content
inventory is not a production corpus. All test stores and artifacts are synthetic;
no paid dispatch or external corpus is involved. Candidate/report identities and
exact counts are in the generated evidence files and CI's uploaded evidence bundle.
