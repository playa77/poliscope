## Original review at the baseline

### Assessment

Four P1 findings should be resolved before the affected contracts are frozen.
Ten P2 findings should become explicit contract decisions and negative tests in
their owning packages. No P0 emergency is established by these documents.

P1 means a documented path can lose promised evidence or produce the wrong
authoritative state. P2 means implementation can make incompatible or unsafe
choices while still satisfying the current broad acceptance wording.

The architecture consistently preserves player agency, Python arithmetic,
shared finite resources, local ownership, optional AI, and honest model coverage.
The main weakness is the definition of state and information boundaries during
failure, replay, import, and multi-request assistance.

### Findings

#### RT-01 / P1 — Historical results are promised but stored as disposable caches

**Type:** cross-document contract conflict.

**Evidence:** `docs/design_doc.md:264` requires explicit model migration rather
than reinterpretation. `docs/tech_spec.md:343` calls evaluations/traces derived
caches; `docs/tech_spec.md:351` permits cache deletion; `docs/tech_spec.md:353`
preserves old results as historical evidence; `docs/tech_spec.md:357` makes
exported cached results optional. Historical inspection without the old runtime
is promised at `docs/tech_spec.md:361` and
`docs/roadmap/work_packages.md:430`.

**Failure case:** commit an evaluated design, discard its caches, remove access
to its exact numeric runtime, and reopen/export it. Inputs and model identities
cannot reconstruct the old numbers or calculation trace. The archive may be
valid but incapable of providing the promised historical evidence.

**Fix:** distinguish durable accepted-result/trace evidence from recomputable
caches. Define the minimum immutable evidence retained per accepted revision and
confirmed boundary, and what exports must carry. If intentionally omitting it,
explicitly label historical results unavailable rather than promise preservation.

**Acceptance:** clear all disposable caches, make the old runtime unavailable,
then reopen and round-trip the archive. Verify retained evidence and its status.
Owners: WP-009/017/018/036/039/041; E2E-015.

#### RT-02 / P1 — Historical mode has no defined route past compatibility rejection

**Type:** conflicting admission rules plus missing fallback contract.

**Evidence:** `docs/tech_spec.md:359` requires compatible mechanisms at import;
`docs/tech_spec.md:361` allows inspection when the required historical model is
unavailable. `docs/tech_spec.md:451` promises readable state on protocol mismatch,
while `docs/tech_spec.md:58` denies renderer database access and the normal reader
is the engine. WP-039 checks compatible mechanisms at
`docs/roadmap/work_packages.md:410`; WP-041 promises historical inspection at
`docs/roadmap/work_packages.md:430`.

**Failure case:** a structurally safe archive contains a historical mechanism
absent from the installed registry. Enforcing compatibility rejects it before
read-only inspection. A cold application start with a protocol mismatch also has
no specified compatible reader for the saved evidence.

**Fix:** separate safe structural admission, supported data/schema readability,
and executable-model compatibility. Define a trusted read-only reader path that
does not execute imported mechanisms or require the unavailable numeric runtime.
State what happens when the archive schema itself cannot be read.

**Acceptance:** cold-start and import with an absent historical mechanism and a
protocol-incompatible engine; display safe historical data, disable computation
and mutation, and continue rejecting unsafe archive structures.
Owners: WP-010/039/041; E2E-006/011/015.

#### RT-03 / P1 — Scheduling a revision does not define which changes become effective

**Type:** missing authoritative-state contract.

**Evidence:** `docs/tech_spec.md:263` says a future policy references an approved
revision; `docs/tech_spec.md:341` stores canonical input snapshots.
`docs/roadmap/work_packages.md:348` schedules approved revisions but does not
define patch, replacement, precondition, or conflict semantics.
`docs/roadmap/domain_work_packages.md:73` distinguishes player choices from
modeled institutional decision processes without defining their adoption link.

**Failure case:** from R0 approve A, which changes education, and independently B,
which changes health. Schedule A for day 10 and B for day 20. Applying B's full
snapshot restores R0 education; interpreting B as a patch preserves A. Neither
the intended behavior nor handling of intervening policy/state changes is fixed.

**Fix:** define a scheduled adoption object containing exact policy delta or
declared replacement semantics, expected base policy identity, target scopes,
preconditions, conflict behavior, and transition/migration rules. Separate policy
adoption from resetting stocks, cohorts, assets, and pending institutional cases.
Clarify how a modeled institution's outcome authorizes an effective change.

**Acceptance:** schedule disjoint and conflicting changes from the same base;
add intervening stock/asset/case changes; verify declared adoption behavior,
same-boundary ordering, and replay without unintended resets.
Owners: WP-018/033/034/036; E2E-009.

#### RT-04 / P1 — The transition algorithm commits before validating invariants

**Type:** unsafe prescribed ordering.

**Evidence:** `docs/tech_spec.md:258` commits the combined transition in memory;
`docs/tech_spec.md:259` validates invariants afterwards.
`docs/roadmap/work_packages.md:357` repeats this order, while
`docs/roadmap/work_packages.md:359` forbids half-boundary persistence and
`docs/roadmap/work_packages.md:381` promises confirmed-state recovery.

**Failure case:** a proposal passes local validation but produces an invalid
combined stock or cohort balance. The specified invariant check fails after the
simulation state is committed. Rollback, visibility to queries, and checkpoint
publication are not defined. Atomicity alone does not make invalid state valid.

**Fix:** stage events and all proposed effects privately; validate the complete
candidate and invariants before publishing/confirming it. Specify persistence,
acknowledgment, cancellation, and rollback ordering. If an in-memory staging step
was intended, name it staging rather than commit.

**Acceptance:** inject an invariant violation and crash/cancel around every
publication step; readers and restart must see only a valid confirmed boundary.
Owners: WP-034/036/053; E2E-007/009/012.

#### RT-05 / P2 — Idempotency lacks replay order, key scope, and payload binding

**Type:** incomplete recovery contract.

**Evidence:** `docs/tech_spec.md:327` combines current-head validation and
operation-ID recovery. `docs/roadmap/work_packages.md:194` promises replayable
outcomes. E2E-005 at `docs/roadmap/verification_matrix.md:94` tests duplication
and a lost reply but does not specify the result lookup contract.

**Failure case:** the first Apply commits and loses its reply. Retrying after
the branch head moves fails the ordinary stale-head check unless the operation
ledger is checked first. Reusing the ID with a different payload or civilization
has no stated error or scope rule.

**Fix/test:** define durable operation-key scope, canonical payload binding,
status lookup, retention, and replay-before-current-head validation for an
already committed identical operation. Reject key reuse with different payloads.
Test identical retry after head advancement, conflicting reuse, and cross-context
reuse. Owners: WP-005/010/018/036/041; E2E-005.

#### RT-06 / P2 — Allocation-dependent outputs are evaluated before allocations

**Type:** ambiguous evaluation algorithm.

**Evidence:** `docs/tech_spec.md:216` evaluates numerical components before
`docs/tech_spec.md:217` constructs accounts and resolves allocations. WP-014
integrates finite-allocation solvers at `docs/roadmap/work_packages.md:154`, but
the orchestration contract does not say which accounts and allocation nodes must
already participate in the numerical graph/SCCs. Shared constraints are required
throughout `docs/roadmap/domain_work_packages.md:122`.

**Failure case:** two services each request 100 energy units and calculate 100
output units. Only 100 energy units exist; the later allocation gives 50 each.
Without allocation-dependent evaluation, outputs still report 200. Coupled
production that supplies another service also needs this feedback in its graph.

**Fix/test:** put claims, allocation, actual consumption, and resulting output
dependencies into the graph before SCC compilation, or define an equivalent
explicit reconciliation algorithm. Test contention and a production/allocation
cycle against independently derived actual outputs. Owners: WP-014/015/016/034.

#### RT-07 / P2 — Private content is not traced through immutable history and exports

**Type:** incomplete information-lifecycle contract.

**Evidence:** `docs/design_doc.md:274` promises independent privacy inclusion
controls. Notes use preview/apply at `docs/tech_spec.md:316`; committed revisions
are immutable at `docs/tech_spec.md:351`; exports include history but have private
content controls at `docs/tech_spec.md:357` and `docs/tech_spec.md:363`.
`docs/roadmap/work_packages.md:513` permits independent transcript deletion.

**Failure case:** a private note or generated proposal is copied into revision
payloads, rationale, traces, archived alternatives, an attachment excerpt, or an
older transcript. Omitting the current note/transcript table leaves the copied
text in a history-inclusive export. A transcript-table deletion may leave a
derived full-text index or attachment copy intact.

**Fix/test:** define private versus public proposal content, sensitive-data
references, mutable/deletable stores, derived-copy ownership, and an explicit
export projection with integrity semantics. State deletion limits for backups
and journals without promising secure erasure. Place synthetic canaries in old
notes, turns, excerpts, and derived records; verify unselected exports and
deleted active records do not retain them in unauthorized locations.
Owners: WP-018/031/039/046/047/049/053; E2E-011/014.

#### RT-08 / P2 — Initial context consent does not specify subsequent disclosure checks

**Type:** missing enforcement detail for an existing privacy requirement.

**Evidence:** `docs/tech_spec.md:419` requires explicit inclusion of broader or
private context; `docs/tech_spec.md:423` permits compare/retrieve/preview tools;
`docs/roadmap/work_packages.md:481` shows the exact initial manifest, and
`docs/roadmap/work_packages.md:482` validates tool arguments/references. The
documents do not define authorization of each newly returned datum before the
next provider request.

**Failure case:** a source excerpt prompts retrieval of additional traces or
another branch; a successful read-only tool returns data not present in the
approved manifest. Immutable revision binding and lack of write tools do not by
themselves authorize sending the result, filenames, errors, or inferred context.

**Fix/test:** make sharing permissions an enforced per-turn capability covering
initial context, tool results, history, attachment derivatives, and continuation.
Authorize every provider-bound expansion; require explicit inclusion outside the
allowed envelope. Test injection requesting excluded private/branch data and
verify provider-visible requests, not only lack of mutation.
Owners: WP-046/047/049/053; E2E-014.

#### RT-09 / P2 — Passive network loads from untrusted rendered content are not forbidden

**Type:** incomplete network trust boundary.

**Evidence:** `docs/tech_spec.md:447` requires restrictive CSP, sanitization,
blocked navigation, and no remote scripts/provider requests. It does not
explicitly forbid passive image/media/CSS/network loads from untrusted content.
Artifacts and attachments require safe handling at `docs/tech_spec.md:435` and
`docs/roadmap/work_packages.md:491`.

**Failure case:** imported Markdown or an AI response contains a remote image
URL with a unique query token. A sanitizer can allow a nonexecutable image while
the renderer sends a request without the explicit sharing action required by
the local-ownership/privacy model. Script blocking alone does not prevent this.

**Fix/test:** require network-denying renderer policies for untrusted content,
local/proxied safe representations where appropriate, and explicit user-mediated
fetch/open behavior. Test images, CSS URLs, SVG references, media, and artifact
links with a controlled network sink; rendering must not emit requests.
Owners: WP-011/047/053; E2E-012/014.

#### RT-10 / P2 — Spending gates lack atomic reservations across in-flight requests

**Type:** incomplete concurrent-request contract.

**Evidence:** `docs/tech_spec.md:433` allows tool continuations;
`docs/tech_spec.md:439` reconciles later costs; `docs/tech_spec.md:441` gates new
requests. `docs/roadmap/work_packages.md:503` and
`docs/roadmap/work_packages.md:505` require pre-request gates without defining
in-flight reservation or unknown-cost rules.

**Failure case:** with a session allowance of 1 unit, two simultaneous requests
each estimated at 0.6 both pass against the same recorded balance. A single turn
can also dispatch several tool-continuation generations without a defined
per-dispatch gate. This is separate from the acknowledged estimate overrun of
an already authorized request.

**Fix/test:** serialize or atomically reserve estimated exposure before every
billable dispatch; define unresolved-cost/cancellation handling and reconcile
reservation to reported cost without double charge. Specify behavior when a
useful estimate is unavailable. Test simultaneous dispatch, tool rounds, late
costs, key removal, and cancellation. Owners: WP-045/046/048/050.

#### RT-11 / P2 — Fixed precision needs a conservation and representability policy

**Type:** reproduced numerical contract edge case.

**Evidence:** `docs/tech_spec.md:185` fixes Decimal precision at 28 digits;
`docs/tech_spec.md:231` specifies conservation. WP-006 names precision fixtures
at `docs/roadmap/work_packages.md:73`, but does not define allowed magnitude/
resolution combinations, rounding residuals, or under-resolution rejection.

**Reproduced:** with precision 28 and round-half-even, start with `1E29` and
withdraw `1` at each of 100 boundaries. The stock remains `1E29`; every rounded
per-boundary check `opening == closing + 1` passes. A 60-digit independent check
finds a total conservation residual of `-100`. This shows the unrestricted
contract permits an invariant to pass while losing the accounting effect.

**Fix/test:** define representable units/magnitudes, account quantization and
explicit residual handling, or reject operations that cannot change the stock
at its declared resolution. Use a higher-precision/integer independent oracle
for boundary fixtures. Do not fix this by silently weakening conservation.
Owners: WP-006/015/034; T §7.1/7.4.

#### RT-12 / P2 — RNG identity does not unambiguously distinguish mechanism instances

**Type:** underspecified identity contract; DEC-02 is the proper resolution point.

**Evidence:** `docs/tech_spec.md:201` has mechanism instances, but stream keys at
`docs/tech_spec.md:242` contain seed, mechanism, scope, and event index.
`docs/roadmap/work_packages.md:367` repeats this tuple; stochastic domain behavior
depends on it at `docs/roadmap/domain_work_packages.md:226`.

**Failure case:** two assets in the same scope use the same hazard mechanism at
event index zero. If 'mechanism' means definition ID, their supposedly isolated
streams collide. Adding a second draw purpose can also shift later draws unless
event and draw identities have stable semantics.

**Fix/test:** explicitly choose stable instance/entity identity, stream purpose,
event identity, draw indexing, and version rules. Distinguish deterministic
stream separation from intended statistical dependence. Test same-definition,
same-scope instances, unrelated insertion, checkpoint resume, and branch forks.
Owners: WP-005/035; DEC-02; E2E-007.

#### RT-13 / P2 — Uncertainty lacks a joint-dependence contract

**Type:** missing model semantics, not a request to invent distributions.

**Evidence:** `docs/tech_spec.md:240` allows ranges/distributions and
`docs/tech_spec.md:242` isolates streams. WP-038 requires uncertainty propagation
at `docs/roadmap/work_packages.md:397`. Cross-domain exposure is shared at
`docs/roadmap/domain_work_packages.md:239`, but no joint-dependence or unknown-
dependence behavior is specified.

**Failure case:** drought reduces water supply and increases care demand.
Independent draws remove their common cause and understate joint shortages.
Likewise, for the same uncertain `x`, `x + (1-x)` is exactly 1; treating each
occurrence as an independent interval yields a misleading range. Reproducible
streams do not establish valid statistical independence.

**Fix/test:** reference shared uncertain variables and explicit joint/sampling
models. Treat unspecified dependence as unsupported or qualify a declared
approximation. Add common-cause and repeated-variable fixtures with independently
derived bounds/probabilities. Owners: WP-008/035/038; DOM-07/10/12.

#### RT-14 / P2 — Cross-milestone scenarios have no explicit gate-specific case lists

**Type:** acceptance ambiguity.

**Evidence:** G2 requires E2E-001–006 'relevant cases' at
`docs/roadmap/verification_matrix.md:168`. E2E-002 at
`docs/roadmap/verification_matrix.md:91` includes target editing delivered by
WP-031 in M3. E2E-006 at `docs/roadmap/verification_matrix.md:95` includes
streaming/provider behavior from M6. Yet M2's headless gate already requires
create/query workflows at `docs/roadmap/work_packages.md:204`, before the final
creation/UI packages are accepted.

**Failure case:** one reviewer demands future functionality and blocks M2;
another excludes crash/save or target-isolation checks as not yet relevant. Both
can cite the same scenario row. Parent acceptance dependencies do not define
these individual evidence selections.

**Fix/test:** split scenarios into stable subcases with first-required milestone,
owning service/child, actual prerequisites, and allowed temporary limitations.
State how creation/query APIs required by WP-019 arrive before UI consumers.
Validate the gate manifest for every milestone, with no unowned mandatory case,
undefined selection, or mock substituting for required production behavior.
Owners: WP-001/003/019/024/055.
